# 다른 PC 간 대전 연결 확인

2026-10-31 연결 진단 기록. 대상은 한국판 SLKA-25153입니다. 당시 `common-fix` 앱의 peer 연결 정보 형식에서 추가 수정이 필요한 차이는 발견하지 못했습니다. 이 점검에서 실행 코드는 변경하지 않았습니다.

**2026-11-01 사용자 추가 확인: 서로 다른 PC 두 대에서 실제 대전이 동작합니다.** 사용자 보고에 따른 확인이며 에이전트가 직접 경기를 관찰한 것은 아닙니다. 아래의 같은 PC 실패와 STUN 시험은 이전 진단 기록이고, 최종 경기 기록 DB 저장·Docker 엔진 실행·모든 NAT 환경 검증을 의미하지 않습니다.

## 확인된 서버 동작

사용자가 제공한 실패 로그에는 양쪽의 `4345 → 4346/4347/4348`, 상대에게 보내는 `4330`, 양방향 `4350` 중계 및 `4b00 → 4b01` 응답이 보입니다. 서버의 제어 정보 교환이 진행되었다는 증거이며, 실제 UDP 대전 연결 성공의 증거는 아닙니다.

원본 PS2 파서를 합성 데이터로 실행해 다음 payload 읽기 길이와 IP·포트 필드를 확인했습니다. IP는 ASCII16, 포트는 network-endian 16bit입니다.

| 패킷 | 본문 길이 | 내용 |
| --- | --- | --- |
| `4b01` | 44 | 상태4 + 주소/포트 두 쌍36 + 프로필 ID4 |
| `4347` | 75 | prefix32 + 주소/포트 두 쌍36 + ID4 + 추가3 |
| `4330` | 79 | prefix36 + 주소/포트 두 쌍36 + ID4 + 추가3 |
| `4350` | 72 | u32 두 개 + 데이터64 |
| `4351` | 770 | u32 다섯 개 + 데이터750 |

모두 현 서버와 일치하고 원본 파서의 본문 밖 읽기는 0이었습니다. 이전 정적 후보 표의 `4350=64`, `4351=750`은 데이터 부분만 센 값이며 전체 본문 길이는 위 표로 정정합니다. 서버는 두 payload를 그대로 중계하므로 실행 코드 수정은 필요하지 않았습니다.

실제 서버 클래스와 wire 직렬화를 사용한 두 클라이언트 회귀를 추가했습니다. 같은 공인 NAT 뒤의 서로 다른 LAN IP가 각각 UDP3658을 광고할 때 주소·포트가 보존되는지, 두 중계 payload가 바뀌지 않는지 검사했습니다. 2026-10-31 당시 전체 Python 회귀 **160개 통과**. 이 합성 검사와 이후 사용자의 실제 두 PC 대전 확인은 별개의 증거입니다.

## 같은 PC 두 인스턴스와 STUN

실패를 재현한 환경은 같은 PC의 두 PCSX2였습니다. 로컬 OS에서 한 프로세스만 UDP3658을 바인딩했고 다른 프로세스에는 임의 UDP 포트들이 관측되었습니다. 두 인스턴스는 같은 설정·로그 경로를 사용했습니다. 이는 같은 PC의 고정 포트 경합이 유력하다는 근거이며, 모든 실패 원인을 확정한 패킷 캡처는 아닙니다.

PCSX2 2.8.2 Sockets는 게임의 UDP 원본 포트를 바인딩하고, 실패하면 목적지별 동적 소켓으로 재시도합니다. 이 경우 STUN 조회에 사용한 포트와 상대 통신에 사용한 포트가 달라질 수 있습니다. [PCSX2 공식 구현](https://github.com/PCSX2/pcsx2/blob/v2.8.2/pcsx2/DEV9/sockets.cpp#L479), [UDP 소켓 구현](https://github.com/PCSX2/pcsx2/blob/v2.8.2/pcsx2/DEV9/Sessions/UDP_Session/UDP_Session.cpp#L130).

현재 사용자 요청에 따라 같은 PC 두 인스턴스용 우회나 설정 변경은 진행하지 않습니다. 서로 다른 PC에서는 이 호스트 포트 경합은 공유하지 않지만, 각 공유기의 NAT·방화벽과 상대 UDP 도달성은 별도입니다.

2026-10-31 진단 PC에서 `46.101.172.11:3478`로 다시 검사한 결과, 한국판의 legacy Binding Request에는 정상 응답했고 CHANGE-REQUEST flags6에는 타임아웃이 발생했습니다. 이는 당시 기본 외부 주소 조회가 동작했다는 기록이며 현재 STUN 가용성이나 전체 NAT 분류를 보장하지 않습니다. 이 결과만으로 STUN 서버 장애와 경로의 NAT 필터를 구분할 수 없습니다.

STUN은 외부 주소를 찾는 기능이고 게임 UDP를 자동 중계하는 기능이 아닙니다. RFC3489도 대칭 NAT 및 같은 NAT 뒤 상대 연결 등의 한계를 명시합니다. [RFC3489](https://www.rfc-editor.org/rfc/rfc3489#section-1). 게임 서버의 UDP3478 포트만 열어도 대전 UDP를 중계하게 되는 것은 아닙니다.

## 이후 연결 문제의 진단

서로 다른 PC 두 대의 실제 대전은 사용자 확인이 있습니다. 다른 환경에서 연결 문제가 생기면 양쪽의 PCSX2 로그와 실패 직후 app 로그를 함께 확인해야 합니다. 서버의 방·경기 시작 성공과 peer 주소 전달만으로 모든 네트워크 환경의 대전 성공을 보장할 수는 없습니다.
